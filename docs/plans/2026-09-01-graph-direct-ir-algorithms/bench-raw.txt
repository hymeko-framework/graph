host: single machine (x86_64 windows, rustc 1.97.1, --release). times are us.
A=direct(node+arc)  B=direct(no arc-visited, k^2 control)  C=sparse-star O(nnz)  D=clique O(Sum k^2)

Warm-query zero allocation: PROVEN by counting global allocator (0 allocs over 32 warm queries).
All five approaches agree on the reachable count (2000-node correctness check).

INTERPRETATION (isolated, honest):
- Direct A is ~13-15x slower to TRAVERSE than the flat-u32 sparse-star CSR (C).
  Discriminator: A ~= B though B does k-fold more member-visits => A's cost is the FAT canonical
  Vec<SignedRefR> iteration + per-incidence is_node kind lookup, NOT the arc-expansion count.
  The flat u32 CSR streams packed integers; the canonical structure chases fat enums. This is the
  price of zero-copy + losslessness (sign/weight/annotation inline via (arc,slot)) + canonical IDs.
- visited_arcs is correct/enforced (debug_assert on double-mark; B re-expands, A does not). Its
  wall-clock win over B is modest because A's per-incidence constant factor dominates.
- Direct BEATS clique on build (4.3x arity5, 9.0x arity20) and memory-vs-blowup; clique query is
  fast only AFTER an expensive O(Sum k^2) build (60-118 ms).
- Mission 3%-vs-sparse-star gate: NOT met for warm query; taken via the "precise profiled
  explanation" branch above. NOT a bug; a structural zero-copy-vs-flat-materialization tradeoff.
- Follow-up (documented, NOT done; would betray zero-copy if made default): an operator-side flat
  Vec<DeclId> target cache would close the traversal gap at the cost of losslessness/coherence.
